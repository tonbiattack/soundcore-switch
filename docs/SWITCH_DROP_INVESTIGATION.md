# 切り替え直後に切断される現象の調査

最終更新: 2026-11-26

> 対象: 「切り替え先の端末でイヤホンが一瞬つながり、そのあと未接続に戻る」現象。
> 実機（Windows / Liberty 4 NC）でプロトコルを直接観測して切り分けた記録。
> 端末名・MAC は匿名化している。

## 1. 症状

- 切り替え操作の直後、接続先の端末にイヤホンが現れる（接続音も鳴る）
- 数秒〜十数秒で未接続に戻る
- アプリ側は「〜に切り替えました」と成功表示していた

## 2. 調査方法

アプリの表示ではなく、**イヤホン自身が報告する接続先一覧**を時系列で記録した。

- Windows から RFCOMM（ベンダー UUID）で直接接続
- `0B 01`（一覧取得）で状態を読み、`0B 81`（切断）/ `0B 82`（接続）を送る
- 一覧は分割パケットで届くため、`total` 件そろうまで読み続ける
  （1回の `recv` だけで読むと取りこぼし、機器が消えたように見える）

調査用スクリプトはリポジトリに含めていない（実 MAC を引数で受けるため）。

## 3. 実測結果

| 対象 | 種別 | 結果 |
|---|---|---|
| 対象A | スマートフォン（起動中） | 接続して**維持される** |
| 対象B | PC（Bluetooth オフ → 後日オン） | オフ時: **一度も接続されない**（`CONNECT` を3回送っても切断のまま）<br>オン後: **約5秒で切断**（2回試行とも） |
| 対象C | PC | 約15秒で切断 |

### 追加の切り分け

| 検証 | 結果 | 意味 |
|---|---|---|
| 送信後、一切通信せず25秒待つ | 切断された | アプリのポーリングは原因ではない |
| 対象Aへ接続 | 維持される | 同じコマンド手順で成功する＝手順の問題ではない |
| 対象B・Cへの ping / DNS | 応答なし | ネットワーク的にも到達できない状態だった |
| イヤホンが PC 未接続のときの RFCOMM | `connect failed (10060)` | 制御チャネルは接続中のリンク経由でしか張れない |

## 4. 結論

- アプリは `CONNECT` を1回送るだけで、**切断コマンドは送っていない**。
- 同じ手順で対象A（スマホ）は維持されるため、**アプリのコマンド手順は原因ではない**。
- イヤホンは接続先と確立できなくても、一覧上はいったん「接続中」と報告し、
  数秒〜十数秒で切断中へ戻す。これが「一瞬ついて戻る」の正体。
- **対象B・C（PC）側が接続を維持できていない。** アプリからは対処できない。

## 5. アプリ側で行った改善

症状そのものは対象側の問題だが、**成功と誤表示しない**ように直した。

| 変更 | 内容 |
|---|---|
| 接続直後の維持確認 | `CONNECT` 後、待ってから一覧を読み直し、切れていれば失敗 |
| 既に接続中の場合の確認 | 一覧で「接続中」でも即成功にせず、維持を確認。切れていれば接続し直す |
| 成功後の再確認（2段階） | 7.5秒と15秒の2回確認し、切れていれば「接続が続きませんでした」へ訂正 |
| 失敗理由の追加 | `SwitchNotRetained`（接続が続かなかった）を新設し、対象端末側の確認を案内 |

関連: [SWITCH_STABILITY.md](./SWITCH_STABILITY.md) §5

## 6. 対象端末側で必要な対処

1. **イヤホンを削除して再ペアリング**
   古いペアリング情報（リンクキー）が残っていると、接続直後に切られることがある。
2. **対象端末から接続してみる**
   端末側から繋いで維持されるなら、イヤホン主導の接続手順に問題がある可能性。
3. **Bluetooth アダプタの設定を確認**
   「電力の節約のためにオフにできる」を無効化、ドライバ更新。
4. **純正アプリで同じ切り替えを試す**
   純正アプリでも切れるなら対象端末側の問題と確定できる。
