## 1. 結論

**実機で接続先一覧の取得と切り替えコマンドの送信に成功した。**

| 項目 | 判定 | 根拠 |
|---|---|---|
| 接続先（マルチポイント登録端末）一覧の取得 | **可（実機確認済み）** | 7台の登録端末と接続状態を取得 |
| 接続先の切り替え指示 | **可（実機確認済み）** | コマンド送信・応答を確認 |
| 切り替え完了の検出 | **可** | 一覧を再取得して `connected` フラグで判定 |
| Android 標準 API のみでの実現 | **不可** | 機種固有プロトコルが必要 |

これにより、仕様書 §6 の縮小案ではなく**本来の目的（ワンタップ切り替え）が実現可能**と判明した。

### 1.1 実装上の最重要事項

**コマンドの応答有無だけでは成否を判定できない。** 実機で次の両方を観測した。

| 操作 | 応答 | 実際の結果 |
|---|---|---|
| 切断（対象A） | あり | 成功 |
| 切断（対象B） | なし | 失敗（拒否） |
| 接続 | なし | 成功 |

そのため、成否は**必ず一覧を再取得して状態で確認する**。
詳細は [VERIFICATION_A40.md](./VERIFICATION_A40.md) §3 を参照。

## 3. プロトコル仕様（実機で解読）

### 3.1 接続方式

**RFCOMM（SPP ではない）** を使う。ベンダー固有のサービス UUID に接続する。

```
UUID = 0cf12d31-fac3-4553-bd80-d6832e7b + <モデルコード4桁>
例: Liberty 4 NC (A3947) → 0cf12d31-fac3-4553-bd80-d6832e7b3947
    Space A40    (A3936) → 0cf12d31-fac3-4553-bd80-d6832e7b3936
```

> **重要**: 標準 SPP UUID (`00001101-...`) に接続すると別のプロトコル
> （`03 01 00 ...` で始まる応答）が返り、目的のコマンドは使えない。
> 必ずベンダー UUID に接続すること。

### 3.2 パケット形式

**ホスト → デバイス**

```
08 EE 00 00 00 | CC CC | LL LL | [body...] | SUM
└─ 固定ヘッダ ─┘ └コマンド┘ └長さ(LE)┘            └チェックサム
```

**デバイス → ホスト**

```
09 FF 00 00 01 | CC CC | LL LL | [body...] | SUM
```

- `LL LL` は **ヘッダ9 + body + チェックサム1** の合計長（リトルエンディアン）。
- `SUM` はチェックサムを含まない全バイトの総和の下位8ビット。

### 3.3 コマンド一覧

| 用途 | コマンド | body |
|---|---|---|
| 状態取得 | `01 01` | なし |
| 接続先一覧取得 | `0B 01` | なし |
| マルチポイント有効/無効 | `0B 84` | `01` / `00` |
| 接続先を切断 | `0B 81` | MAC 6バイト |
| **接続先へ接続（切り替え）** | `0B 82` | MAC 6バイト |
| 接続先を削除 | `0B 83` | MAC 6バイト |

### 3.4 接続先一覧の応答形式

応答は**複数パケットに分割**される。body の先頭2バイトが `総パケット数, このパケットの番号(1始まり)`。

以降は端末ごとに:

```
[長さ1] [接続フラグ1] [MAC 6] [名前 (長さ-8 バイト、0 埋め)]
```

`長さ` は自身を含む。実測では 40 バイト固定（名前欄 32 バイト）。

### 3.5 実機で取得した実際の応答

```
TX: 08 EE 00 00 00 0B 01 0A 00 0C
RX: 09 FF 00 00 01 0B 01 AC 00 | 02 01 | ... (1パケット目)
    09 FF 00 00 01 0B 01 84 00 | 02 02 | ... (2パケット目)
```

デコード結果:

| 接続 | MAC | 名前 |
|---|---|---|
| ✅ 接続中 | 7A:A7:6A:03:DD:08 | OPPO Reno13 A |
| ✅ 接続中 | 90:FB:C5:9D:28:F4 | DELLTOWER |
| — | DA:48:59:8A:E9:D4 | CXDEPC26100444 |
| — | 00:B3:2C:83:80:D8 | DESKTOP-ILQVMVD |
| — | 8F:A5:32:05:AE:D0 | Redmi Pad SE 8.7 |
| — | 82:B0:C1:77:6D:FC | MPC144 |
| — | 25:65:08:37:A3:64 | REDPINE_GATT_V02 |

### 3.6 切り替えの制約（実機で確認）

`0B 82` + MAC を送信しても、**既に2台接続中だと3台目は接続されない**。
マルチポイントの同時接続上限が2台のため、これは正常な挙動である。

```
TX: 08 EE 00 00 00 0B 82 10 00 00 B3 2C 83 80 D8 4D
→ 再取得しても DESKTOP-ILQVMVD は connected=0 のまま
```

**したがって切り替えの実装は次の順序が必要:**

1. 現在接続中の端末を特定する。
2. 上限（2台）に達していて、対象が未接続なら、**先に1台を切断**する。
3. 対象へ接続コマンドを送る。
4. 一覧を再取得し、対象が `connected=1` になったことを確認する。

この「先に切断する」処理を省くと、切り替えは必ず失敗する。
本アプリの `SwitchTargetUseCase` は 4 の確認までを担う。

## 4. 実装アーキテクチャ

プロトコル処理は Android / Windows で完全に共通化できる。
トランスポート（RFCOMM ソケット）だけがプラットフォーム依存。

```
:core
  protocol/SoundcoreProtocol.kt   ← パケット生成・解析・一覧デコード（純 Kotlin）
  protocol/SoundcoreTransport.kt  ← RFCOMM 送受信のインターフェース
  adapter/SoundcoreMultipointAdapter.kt ← MultipointAdapter 実装

:app (Android)   → BluetoothSocket によるトランスポート
:desktop (Win)   → Winsock AF_BTH によるトランスポート
```

## 6. 再現手順

プロトコルを直接叩いて確認するためのスクリプトを同梱している。

```powershell
# イヤホンを PC に接続した状態で実行する
.\scripts\probe-soundcore.ps1 -Mac <MACアドレス> -ModelCode <機種コード4桁>

# 例: Space A40 (A3936)
.\scripts\probe-soundcore.ps1 -Mac 880E85018154 -ModelCode 3936
```

このスクリプトは次を並べて表示する。

- イヤホンが報告する接続先一覧と接続状態
- Windows が認識している接続状態（独立した情報源）

両者が食い違うことで、応答と実効果のずれに気づける。

手動で試す場合の手順:

```powershell
# 1. イヤホンを PC に接続しておく
# 2. ベンダー UUID で RFCOMM 接続し、GET_DEVICES を送る
#    （実装は desktop モジュールの SoundcoreRfcommTransport を参照）

# 3. 一覧が返ることを確認
# 4. 0B 82 + MAC で切り替えを試す（2台接続中は先に切断が必要）
```
